# Mega Clean CRM

A small single-user web app for the owner of Mega Clean (a small cleaning business) to:

- Build the weekly staff roster from recurring cleaning patterns and send reminder texts to clients the night before their clean.
- Reconstruct a month of completed jobs at month-end for the accountant (with CSV export).

This is the **Phase 1 MVP** — see [Deviations & Phase 2](#deviations--phase-2-ideas) below.

## Tech stack

- **Client**: Vite + React 19 + TypeScript, Tailwind CSS, wouter for routing, react-hook-form + zod for forms, date-fns for dates. Hand-rolled UI primitives (Button, Input, Select, Card, Modal, Table) in `client/src/components/ui.tsx` — no external UI kit.
- **Server**: Express + tRPC (typed API, no REST boilerplate), Drizzle ORM over Postgres (`postgres`/postgres-js, Supabase-hosted), zod input validation.
- **Auth**: a single hardcoded admin password (env var), gating a signed session cookie. No per-user accounts — this app has exactly one login (the business owner). Employees never log in; they only see printable/shareable schedule pages generated by the owner.

## Project layout

```
server/   Express + tRPC API + Drizzle/Postgres
client/   Vite + React frontend
```

The client imports the server's `AppRouter` **type only** (no runtime code) directly from `../server/src/routers/root.ts` for end-to-end type safety between client and server — this is why both packages live in one repo/workspace.

## Getting started

Requires Node.js 20+.

```bash
npm install                 # installs root + client + server (npm workspaces)
cp server/.env.example server/.env
cp client/.env.example client/.env   # optional — defaults already point at localhost:4000
# then set DATABASE_URL and DIRECT_URL in server/.env to a real Postgres (Supabase) instance
npm run db:migrate          # applies the schema to that database
npm run dev                 # runs the API (port 4000) and the Vite dev server (port 5173) together
```

Open http://localhost:5173 and log in with the password from `server/.env` (`ADMIN_PASSWORD`, defaults to `changeme123` for local dev — **change this before deploying anywhere real**).

## Data model

See `server/src/db/schema.ts` for the full Drizzle schema:

- **clients** — contact info, service types, default frequency/day/time/duration, a `defaultEmployeeId` (a lightweight suggested-default field only — not wired to any pattern/job automation, see [Multiple employees on a job](#multiple-employees-on-a-job)), access notes (key codes, alarms, pets, parking), billing rate + type, status.
- **employees** — contact info, qualified service types, hourly pay rate, status, a weekly availability pattern (JSON), plus a separate **employee_time_off** table for date-range leave.
- **recurring_patterns** — per-client recurring cleans (service type, frequency, **one** day of week, time, duration) that feed the roster generator. `frequency` is one of `weekly`, `fortnightly`, `every-3-weeks`, `monthly`, `one-off`. `every-3-weeks` carries an optional `anchorDate` (falls back to the pattern's `createdAt` date) since a 3-week cycle needs a fixed reference point to know which week is "week 1" — see [Deviations](#deviations--phase-2-ideas). A client cleaned multiple times a week (e.g. Mon/Wed/Fri) just has multiple pattern rows, one per day — see [Multiple days a week](#multiple-days-a-week) for how the client detail page's form handles adding them together. Which employee(s) a pattern is assigned to lives in the separate **recurring_pattern_employees** join table — see [Multiple employees on a job](#multiple-employees-on-a-job).
- **jobs** — one row per scheduled clean, with status, actual hours, completion notes, a `clientResponseStatus` (`confirmed` | `change-requested`, independent of `status` — see [Two-stage messaging](#two-stage-messaging--client-response-status)), and an optional link back to the recurring pattern that generated it (`null` = one-off job). Which employee(s) are assigned lives in the separate **job_employees** join table — see [Multiple employees on a job](#multiple-employees-on-a-job).
- **job_employees** / **recurring_pattern_employees** — many-to-many join tables assigning one or more employees to a job / recurring pattern. See [Multiple employees on a job](#multiple-employees-on-a-job).
- **week_approvals** — one row per week the owner has explicitly approved, keyed by `weekStart` (the Monday, `YYYY-MM-DD`, primary key) with an `approvedAt` timestamp. See [Week approval](#week-approval).

## Multiple employees on a job

Many houses only need one cleaner, but some get cleaned by **two employees at once** — one client, one visit, one time slot, but more than one cleaner assigned (e.g. a job planned for 4 hours takes 2 with two people there together). `jobs` and `recurring_patterns` no longer carry a single `employeeId`/`defaultEmployeeId` column; assignment is many-to-many via two join tables:

- **job_employees** (`jobId` → `jobs.id`, cascade-deletes with the job; `employeeId`, no FK — deleting an employee unassigns them from a job rather than orphaning or cascade-deleting the job's own history, same rationale the old `jobs.employeeId` column used to carry).
- **recurring_pattern_employees** (`patternId` → `recurring_patterns.id`, cascade-deletes with the pattern; `employeeId`, no FK, same rationale).

A pattern's assigned employees carry through automatically to every job `generateWeek` creates from it. `jobs.create`/`update`/`reschedule` and `recurringPatterns.create`/`update` all take an `employeeIds: number[]` array instead of a single `employeeId`. `jobs.list`/`byId`/`upcomingReminders`/`monthlyExport` (and the dashboard's job summaries) return `employeeIds`/`employeeNames` arrays per job instead of the old singular `employeeId`/`employeeName`.

**Billing is unaffected** — `clients.billingRate`/`billingRateType` stays per-job (per-visit or per-hour), never split per employee. A job with two employees assigned bills exactly the same as one with a single employee.

**Conflict detection** (`computeConflicts`) runs its double-booking/time-off/qualification checks **per assigned employee** on a job, not once per job — a job with two employees is flagged if *either* one is double-booked, on time off, or unqualified, with a separate message naming which specific employee is affected (e.g. "Alice is double-booked on…", not a vague combined message).

The employee picker on `JobModal`, `RecurringPatterns` (add and edit), and `RescheduleModal` is `SearchMultiSelect` (`client/src/components/SearchMultiSelect.tsx`) — a multi-select sibling of the single-select `SearchSelect` combobox, with selections shown as removable chips above the search input. The roster's by-employee grouping view lists a job under *every* employee assigned to it, not just one; `PrintWeek` prints a shared job on every one of its assigned employees' pages (with a "With" column naming who else is on it); and the Tomorrow/Heads-up message templates say "with Alice and Bob" for two employees, "with Alice, Bob and Carol" for three or more, and fall back to "our team" when nobody's assigned.

`clients.defaultEmployeeId` is untouched by this — it stays a single-value suggested default on the client record, not wired to pattern/job assignment, and the Clients CSV's `defaultEmployeeName` column is unrelated and unchanged.

### Editing a recurring pattern

Each pattern row on the client detail page now has an **Edit** action (alongside Activate/Deactivate/Delete) that opens the same field set as the "add pattern" form — service type, frequency, day, time, duration, assigned employees — pre-filled with that pattern's current values, and saves via `recurringPatterns.update`. Unlike the add form (which creates one pattern per day when multiple days are selected), editing an existing pattern always edits it as the single-day/single-employee-set row it actually is — it never re-expands into multiple rows.

The four service types (`Deep cleaning`, `Regular cleaning – commercial`, `Regular cleaning – domestic`, `Carpet cleaning`) are a fixed list defined in `server/src/constants.ts` (mirrored in `client/src/lib/constants.ts` for the UI) — intentionally not user-editable in Phase 1.

## Feature tour

- **Clients** (`/clients`) — searchable/filterable list (alphabetical by name), fast-entry add form (only name + phone required), detail page with prominent access notes and inline recurring-pattern management. A client can be permanently deleted from their detail page — normally only if they have no job history yet (jobs.clientId cascades on delete, so a client with real history would silently take their invoicing/roster records with them), but a force-delete option is offered once blocked, for cleaning up a test/mistaken entry that already picked up job history — see [Deleting a client or employee](#deleting-a-client-or-employee). Deactivate remains the non-destructive alternative that keeps history intact.
- **Employees** (`/employees`) — list (alphabetical by name), add/edit, active/inactive toggle, time-off date ranges. Same permanent-delete-with-force-option rule as Clients — see [Deleting a client or employee](#deleting-a-client-or-employee).
- **Roster** (`/roster`) — four views, switchable via tabs: a **Month** calendar (the default landing view — a traditional weeks-as-rows/days-as-columns grid for the whole month, each date cell showing a job count and amber conflict/client-response indicator dots; clicking any date opens that day close-up on the Today page, `/today/:date`) plus the original three week-scoped views — by-day, by-employee, and a **week grid** (day-of-week columns, jobs stacked within each — scrolls horizontally on mobile, `overflow-x-auto`, same as any other wide table in this app). "Generate this week from patterns" turns active recurring patterns into job rows for the displayed week (idempotent — re-running skips dates that already have a job for that client, and survives reschedules, see below); this and the week-approval controls only apply to the three week-scoped views; the Month view is browse/navigate-only, since "generate"/"approve" are single-week concepts. Edit, reschedule, cancel, complete, or **permanently remove** any job, or add a one-off job, from the week-scoped views (the week grid opens the same edit modal on click) — see [Deleting a job](#deleting-a-job) for the difference between Remove and Cancel. Roster conflicts (double-booking, employee on time off, employee not qualified for the service) are flagged inline and recomputed live on every load — see [Conflict detection](#conflict-detection). A job flagged "client requested a change" (see [Two-stage messaging](#two-stage-messaging--client-response-status) below) gets the same amber warning treatment but with its own icon/label so it's never confused with a scheduling conflict — a job can have either, both, or neither. A printable per-employee weekly view is linked from the by-employee tab. Also has an **"Approve this week"** marker for the owner's own peace of mind once she's happy with the week — see [Week approval](#week-approval).
- **Today** (`/today`, or `/today/:date` to deep-link a specific day — e.g. from the Month calendar) — a focused, single-day view for confirming what actually happened, day by day, as the week runs (rather than scanning the whole roster grid). Defaults to today with prev/next day navigation and a "Jump to today" shortcut once you've stepped away; every job scheduled that day gets a card with a quick "Mark complete" / "Cancel" / **"Remove"** action if still outstanding (see [Deleting a job](#deleting-a-job)), or a clear resolved badge (+ hours) and an "Edit" affordance if already settled. A day-level "X of Y jobs confirmed" summary sits at the top, with an all-done empty state once nothing's left outstanding. Reuses the exact same `jobs.complete`/`jobs.cancel`/`jobs.remove` mutations and `CompleteJobModal`/`CancelJobModal` as the roster — this is a filtered view over the same jobs, not a separate system.
- **Tomorrow's messages** (`/tomorrow`) — every scheduled/confirmed job for tomorrow with a pre-filled reminder text and a Copy / Copy all button.
- **Heads-up messages** (`/heads-up`) — the first stage of the two-stage messaging flow: every scheduled/confirmed job in whichever week is currently selected (same prev/next week picker as the roster, not hard-coded to "next week") with a pre-filled "just a heads-up, you're booked in…" message, Copy / Copy all, same as Tomorrow's messages. Purely a message-drafting screen — copying (or not copying) a message has no effect anywhere else in the app.
- **Invoice prep** (`/invoicing`) — pick any From/To date range (defaults to month-to-date), see every completed (and partially-completed-then-cancelled) job in that range grouped by client with computed totals in euros, export to CSV. Includes paused/inactive clients' history. Plain cancelled jobs (no work done) never appear here.
- **Import** (`/import`) — bulk CSV import for Clients and Employees, with a validated preview before anything is committed — see [CSV import](#csv-import).
- **Dashboard** (`/`) — the four Phase 1 stats (this week's job count, month-to-date revenue, unresolved roster conflicts, jobs awaiting completion) plus three lightweight Phase 2 sections aimed at a phone-in-the-evening glance: today/tomorrow's remaining jobs, the active conflicts list (with day/time and a link into the roster), and jobs awaiting completion confirmation with an inline "mark complete" button. Deliberately kept to "at a glance" — no charts, trends, or full analytics.

## Cancellation & reschedule model

A job's `status` is one of `scheduled`, `confirmed`, `completed`, `cancelled`, `cancelled-partial`, `rescheduled` (`rescheduled` is a legacy/reserved value — see below). The two cancellation statuses encode two different real-world situations rather than forcing the owner to mis-mark a job as "completed" just to get paid:

- **`cancelled`** — nothing was done. The client cancelled ahead of time (or the owner is reversing a mistaken "completed"). `actualHours` is cleared to `null`. It's excluded from the invoice export and from active conflict detection, and shows struck-through/greyed on the roster rather than disappearing outright (so there's still a record of what was booked).
- **`cancelled-partial`** — real work happened before/around the cancellation: a partial visit, or a job the owner had already marked `completed` that the client later disputed or cancelled, where the crew still did the work and should still be paid. `actualHours` (and optional `completionNotes`) are recorded and preserved, and the job **still counts toward revenue in the monthly invoice export**, exactly like a normal `completed` job — the invoicing/dashboard revenue queries treat `completed` and `cancelled-partial` as the same "billable" set.

Both are reached through a single `jobs.cancel` mutation (`{ id, actualHours?, completionNotes? }`) — passing a positive `actualHours` produces `cancelled-partial`, omitting it (or passing 0) produces plain `cancelled`. The Cancel button on the roster opens a small modal that asks "no work done" vs "work was done first" up front, so the owner never has to remember the rule. This mutation is intentionally allowed from any current status (including `completed`), which is what makes the "reverse a completed job into a paid partial cancellation" case possible. The `JobModal` (plain edit) no longer exposes cancellation as a raw status option — cancelling always goes through this flow so the hours are captured correctly.

**Rescheduling** (`jobs.reschedule`) moves a job's date/time (and optionally employee) **in place on the same row** — it never creates a new Job and orphans the old one, so the roster/weekly grid immediately reflects the new date and nothing duplicates. Status resets to `scheduled` since the new slot needs reconfirming. It's blocked once a job is `completed`/`cancelled`/`cancelled-partial` (reverse or re-add instead).

To keep `generateWeek` idempotent across reschedules, `jobs.originalDate` records the date a pattern-generated job was *originally* created for, separately from `jobs.scheduledDate` (which moves on reschedule). `generateWeek`'s duplicate check now skips a slot if **either** (a) any job already sits on that client+date (the normal case, and it also catches a job rescheduled *into* a date the pattern would generate for), **or** (b) a job from that same recurring pattern was originally generated for that date, even if it has since moved elsewhere (this is what stops regenerating the week a job was rescheduled *out of* from recreating a duplicate at the old slot).

## Two-stage messaging & client response status

The reminder flow is two independent stages, matching how the owner actually works:

1. **Heads-up** (`/heads-up`) — early in the week, draft-and-send a "just a heads-up, you're booked in for X on [day] at [time]" message for every scheduled/confirmed job in the selected week. Purely a drafting screen (same pattern as Tomorrow's messages): a per-job Copy button, a Copy-all button, toast feedback on copy. It does **not** send anything itself, does not wait for or track replies, and nothing else in the app is gated on "all clients replied" — the owner copies and sends manually via her own phone.
2. **Client response status** — if a client replies (by phone/text, outside the app) wanting a different time, the owner goes to the roster and uses the job's "Mark: client requested change" action to flag it. This sets `jobs.clientResponseStatus` to `"change-requested"` (default `"confirmed"`), which is a field **entirely independent of the job's own lifecycle `status`** (scheduled/confirmed/completed/cancelled/cancelled-partial) — it only tracks whether the client raised an issue with the currently-scheduled slot, not whether the job itself happened. Once resolved (e.g. the job is rescheduled, or the client came back to confirm), the owner clears it back to `"confirmed"` with the same toggle, now labelled "Mark confirmed". Both directions show a toast and immediately re-flag/un-flag the job everywhere it's displayed.

On the roster, a `change-requested` job gets the same amber warning-card treatment as a scheduling conflict (for visual consistency — "something here needs your attention") but with its own icon and label text ("Client requested a change") so the two are never confused; a job can be flagged for a conflict, a client response, both, or neither, independently.

The `jobs.setClientResponseStatus` mutation is the only way this field changes — `jobs.create` and `generateWeek` never pass a value for it, so every new job picks up the column default (`"confirmed"`) automatically.

## Week approval

A lightweight, purely owner-facing go/no-go marker, separate from both the messaging flow above and any individual job's `status`/`clientResponseStatus`. The real-world flow: the owner sends heads-up messages for a week, clients who have an issue text her back and she flags the affected job(s) "client requested a change" on the roster, and once she's satisfied the week is in good shape (or has decided to proceed anyway — entirely her call, nothing here is enforced) she clicks **"Approve this week"** on the roster's week header.

- Backed by a single `week_approvals` table — one row per week, keyed by `weekStart` (the Monday, same week-identity convention `Roster.tsx`/`generateWeek` already use), with an `approvedAt` timestamp. `weekApprovals.approve` upserts (re-approving after unapproving just overwrites the timestamp), `weekApprovals.unapprove` deletes the row, `weekApprovals.get` returns the row or `null`.
- If any job in the displayed week is still flagged `client-requested-change`, an informational note ("N jobs still flagged for a client response") shows next to the Approve button — **this never blocks approval**, consistent with the rest of the app's "don't gate on every client replying" principle.
- Once approved, the roster shows a green "Approved" badge with the approval date/time and a small "Unapprove" link to revoke it (e.g. after a late cancellation changes the picture).
- Approving/unapproving a week **never touches any job** — no job's `status`, `clientResponseStatus`, hours, or anything else changes. It's independent state, purely for the owner's own tracking.

## Deleting a job

`jobs.remove` **permanently deletes** a job row — distinct from `jobs.cancel`, which keeps a `cancelled`/`cancelled-partial` record. It's for the "I scheduled this by mistake, it should just disappear" case (a generation error, a wrong one-off entry), not a real cancellation worth keeping a trace of.

- **Blocked once a job carries billable history** — `completed` or `cancelled-partial` — since deleting those would silently erase real invoicing data with no record. The server rejects the request with a message pointing at Cancel instead (which already handles reversing a mistaken "completed" while keeping a trace). Any other status (`scheduled`, `confirmed`, `cancelled`, `rescheduled`) can be removed.
- A **completed** job can't be deleted directly, but both the roster and Today job cards now offer a "Reverse" action (reuses `CancelJobModal`'s "No work done" path — the same mechanism as any other cancel) that flips it back to plain `cancelled` first; from there it's a normal deletable job. Without this, a mistakenly-completed job was a dead end in the UI — `jobs.cancel` never actually had a status guard against reversing a completed job, the roster just wasn't exposing the button.
- Available from the roster's by-day/by-employee job cards (a trash-icon action alongside Edit/Complete/Reschedule/Cancel) and from the Today page's job cards, both behind a confirmation prompt.
- If the removed job came from an active recurring pattern, the next "Generate this week" simply recreates it — same as if it had never been generated. No special-case handling needed there.
- Same "permanent delete, but only when there's no history to lose" principle as deleting a Client or Employee (see below) — consistent guardrail across the app rather than a one-off rule just for jobs.

## Deleting a client or employee

`clients.remove`/`employees.remove` default to the same guardrail as `jobs.remove`: blocked once the record has any job history, since deleting it would either cascade-destroy that history (clients — `jobs.clientId` cascades on delete) or orphan it (employees — `job_employees.employeeId` isn't a real FK, so old assignment rows would silently point at a deleted employee).

Unlike jobs, though, a client or employee can pick up job history "by accident" — trying out the app, a test entry made while learning the CSV import, etc. — where the owner genuinely does want it gone, history and all. So both mutations accept `force: true` to bypass the block:

- **Client force-delete**: deletes the client's recurring patterns explicitly, then the client row — `jobs.clientId`'s cascade takes care of their jobs automatically. Full removal, nothing left behind.
- **Employee force-delete**: the employee's rows in `job_employees`/`recurring_pattern_employees` are **deleted** (unassigning them from those specific jobs/patterns), not the job/pattern rows themselves — an employee's own record disappearing shouldn't also erase the client-side job/invoice history of work that was actually done, and any co-assigned employee on a shared job stays assigned. Time-off records and any `defaultEmployeeId` reference (on the client record) are cleared the same as a normal delete.
- The client-side flow is a staged confirmation, not a raw "force" checkbox: the first delete attempt gives the normal block message; the UI catches that specific error and asks a second, more explicit question ("Force delete anyway? This will permanently remove their job/billing history too") before retrying with `force: true`. A first-time or never-used record still deletes in one confirmation, same as before — the extra step only appears when there's actually something to lose.

## Searching clients and employees in forms

Any place the app asks the owner to pick a client or employee — the roster's one-off job form, rescheduling, a client's default employee, a recurring pattern's employee(s) — used a plain HTML `<select>`, which only lets you jump between options by typing their first letter (and resets after a pause), unusable once there are 60+ names in one list. `client/src/components/SearchSelect.tsx` replaces single-choice pickers with a type-to-filter combobox (filters by substring anywhere in the name, not just the start; arrow keys + Enter to navigate; a clear button once something's selected). Its sibling `client/src/components/SearchMultiSelect.tsx` handles the employee-assignment pickers that can take more than one employee (job/pattern/reschedule) — same filtering and keyboard nav, with selections shown as removable chips above the input; see [Multiple employees on a job](#multiple-employees-on-a-job). `clients.list`/`employees.list` are also now sorted alphabetically by name server-side (case-insensitive), rather than newest-first, so every one of these lists — and the plain list pages themselves — reads in a predictable order.

## Multiple days a week

A client cleaned 2–3 times a week (or more) needs one `recurring_patterns` row per day — the table itself was already fine with that, `generateWeek` just iterates every active pattern independently regardless of how many share a client. The gap was the client detail page's "add pattern" form only ever let the owner pick one day at a time, meaning 2–3 separate trips through the form for a client cleaned that often.

The day field is now a multi-select chip row (Mon/Tue/Wed/…) instead of a single dropdown. Selecting more than one day and submitting creates one pattern per day selected — same service type, frequency, time, duration, and assigned employee(s) on all of them — via a sequential `recurringPatterns.create` call per day, with a single summary toast ("3 recurring patterns added") rather than one per day. This composes with [multi-employee assignment](#multiple-employees-on-a-job): selecting Mon/Wed/Fri + Alice/Bob creates 3 patterns, each assigned to both Alice and Bob. No schema change beyond the join tables described above; this is purely a client-side form/UX change over the same one-pattern-per-day data model.

## Conflict detection

`computeConflicts(from, to)` (`server/src/conflicts.ts`) is a pure, stateless read: on every call it re-queries current jobs, employee time-off, and employee qualifications and recomputes from scratch — nothing is cached from generation time. Practically, that means:

- Marking an employee on time-off/sick leave **after** jobs were already generated and assigned retroactively flags every affected existing job the next time conflicts are queried (no regeneration needed).
- Editing an employee's qualified service types after jobs were assigned retroactively flags jobs for service types they're no longer qualified for.
- Rescheduling a job onto a slot that now double-books the employee, or onto a day they're unavailable, is flagged as soon as the reschedule is saved (the roster invalidates the conflicts query on every mutation).
- Only non-`cancelled`/non-`cancelled-partial` jobs are considered — cancelling one of two double-booked jobs immediately clears the conflict on the remaining one.
- Overlap is a real interval check (`start < otherEnd && otherStart < end`), so back-to-back jobs for the same employee (e.g. 9–11am then 11am–1pm) are correctly *not* flagged — only actual time overlaps count.

## CSV import

`/import` supports two CSV uploads — Clients and Employees — with client-side parsing (`papaparse`) and a full validation preview before anything is written. Only rows with zero errors **and** no detected duplicate are committed; every other row is skipped and the reason shown. Enum-like fields (service types, frequency, status, etc.) are matched case-insensitively but strictly against the same fixed vocab used everywhere else in the app — an unrecognized value blocks that row with a clear message rather than being silently dropped or guessed.

**Duplicate handling**: a row is treated as a duplicate (and skipped, never silently double-created) if its name+phone (case-insensitive, trimmed) exactly matches an existing client/employee already in the database, *or* an earlier row already in the same CSV file.

Prepare your files as plain CSV with a header row exactly matching the column names below (case-insensitive is fine for the header text itself is not required, but stick to these names — the importer does not fuzzy-match different column names). Leave a cell blank to use the default.

## Deploying (Render)

The app deploys as a **single Render Web Service**. In production the Express server serves the built Vite frontend as static files (see the `if (IS_PRODUCTION)` block in `server/src/index.ts`) and answers the API on the same origin at `/trpc`, so there's no separate static site / CORS setup to configure — one service, one URL.

**Build Command**
```
npm install && npm run build
```
This installs both workspaces and builds the server (`tsc`) and client (`vite build`) into `server/dist` and `client/dist`.

**Start Command**
```
npm start
```
This runs any pending Drizzle migrations (`npm run db:migrate -w server`, idempotent — safe to run on every deploy/restart) and then starts the compiled server (`node server/dist/index.js`).

**Environment variables to set in Render's dashboard**

| Variable | Required | Notes |
|---|---|---|
| `ADMIN_PASSWORD` | Yes | The owner's login password. The `changeme123` dev default in `.env.example` must be overridden — the code has no built-in production guard against using it. |
| `SESSION_SECRET` | Yes | Random secret used to sign the session cookie (e.g. `openssl rand -hex 32`). Must be overridden from the dev default. |
| `NODE_ENV` | Yes | Set to `production`. This is what switches the server into "serve the built frontend" mode. |
| `DATABASE_URL` | Yes | Pooled Postgres connection string (Supabase PgBouncer, port 6543, `?pgbouncer=true`) the running app uses for all queries. |
| `DIRECT_URL` | Recommended | Direct, non-pooled Postgres connection string (port 5432) used by `db:migrate`/drizzle-kit; falls back to `DATABASE_URL` if unset, but a real direct connection is strongly preferred since migrations need transaction/DDL support PgBouncer's pooled mode doesn't provide. |
| `PORT` | No | Render sets this automatically and the server already reads `process.env.PORT` (falling back to `4000` only for local dev) — don't override it. |
| `CLIENT_ORIGIN` | No | Only matters for cross-origin dev setups; harmless to leave unset in production since the frontend is served same-origin. |

`VITE_API_URL` (client-side) is **not** needed in production — it's a build-time variable that defaults to same-origin (`""`, i.e. relative `/trpc` requests) whenever the client is built with `NODE_ENV=production`/Vite's production mode, which `vite build` sets automatically. Don't set it in Render unless you deliberately split the frontend and API into separate services later.

**Database:** the app is backed by a Supabase-hosted Postgres instance (Drizzle ORM over `postgres`/postgres-js), not a local file — Render's ephemeral filesystem is no longer a concern for data persistence. Set `DATABASE_URL` (pooled) and `DIRECT_URL` (direct) in Render's dashboard as above; `npm start` runs `db:migrate` against `DIRECT_URL` before the server boots.

**Confirmed already in place:**
- The server reads its port from `process.env.PORT` (`server/src/index.ts`), falling back to `4000` only when unset — Render's dynamically assigned port is picked up automatically.
- `.env` and any `.env.*` variant are listed in `.gitignore` (`.env.example` files excepted), and only `server/.env.example` / `client/.env.example` are committed. `git log --all` shows no `.env` file has ever been tracked or pushed to GitHub.

## Deviations & Phase 2 ideas

Deviations from the spec made during the build, with rationale:

- **Fortnightly / monthly recurrence** is generated with a simple deterministic rule (fortnightly: even ISO week numbers; monthly: only the first occurrence of the weekday in the calendar month) rather than tracking an explicit per-pattern anchor/offset. This keeps the schema simple; a real fortnightly cadence anchored to an arbitrary start date is a good Phase 2 refinement. **`every-3-weeks`** (added later, at the owner's request) *does* carry a per-pattern `anchorDate` — a 3-week cycle can't get away with the "global parity" trick fortnightly uses, since there's no notion of "every 3rd ISO week" that means the same thing to everyone. If left blank when creating the pattern, it defaults to the pattern's own `createdAt` date, so "every 3 weeks starting from whenever I added this" just works without asking the owner to think about anchor dates for the common case.
- **"Generate next week"** generates jobs for whatever week is currently displayed in the roster (with prev/next navigation), rather than being hard-coded to "next calendar week" — this is more flexible for catching up if a week was missed.
- **Employee CRUD was built (and committed) before Client CRUD**, reversing the spec's listed order — the client form's "default employee" field needs the employees list to exist for a typed tRPC call, so employees had to land first.
- **Sessions are stateless** (signed cookie, no server-side session table) since there's only ever one logged-in user — simpler than adding a sessions table for no real benefit at this scale.
- **`cancelled-partial` is a new job status**, not part of the original Phase 1 `JOB_STATUSES` — see [Cancellation & reschedule model](#cancellation--reschedule-model) for the reasoning. The pre-existing `rescheduled` status is left in the enum for backwards compatibility but is no longer set by the app — `jobs.reschedule` moves a job in place and resets it to `scheduled` instead of using a separate status, so the roster only ever needs to look at one row per job.
- **CSV import runs entirely client-side** (parsing with `papaparse`, validation in `client/src/lib/csvImport.ts`) and commits by calling the existing `clients.create` / `employees.create` mutations once per valid row, rather than adding a dedicated bulk-insert endpoint — simplest option for a one-time ~65-row import, and it reuses the exact same server-side validation every other create path goes through.

- **Responsive nav**: `Layout.tsx` renders the same `NAV_ITEMS` list two ways — a fixed bottom tab bar below Tailwind's `md:` breakpoint (unchanged from earlier phases, correct for one-handed phone use) and a fixed left sidebar (logo, stacked nav, logout) at `md:` and up, switched purely with responsive Tailwind classes (`hidden md:flex` / `md:hidden`) rather than JS viewport detection, to avoid layout flash. The header's logo only shows on mobile (the sidebar's logo replaces it on desktop); the logout button stays in the header at both breakpoints, plus a second copy at the bottom of the desktop sidebar.
- **Roster calendar-grid view** is a simple stacked-card-per-day-column layout, not a true pixel-positioned time-axis calendar — enough to read "what's on Tuesday vs Wednesday" at a glance without the complexity of real time-slot geometry. The by-day view remains the default and is still the better choice one-handed on a phone; the calendar grid is there for when a wider side-by-side view is wanted, and needs horizontal scroll on narrow viewports (same `overflow-x-auto` pattern the `Table` component already uses).

Explicitly out of scope for this round (per the spec) and left for later:

- Notifying clients automatically on cancellation/reschedule (currently the owner still texts them manually, same as the existing "Tomorrow's messages" flow).
- Payroll, quotes, job photos, employee accounts/logins.
- Dashboard analytics beyond the lightweight "at a glance" sections above (trends, charts, per-employee performance, etc.).
